## 1. 项目边界与共识

- 这是一款“大学经营模拟”网页游戏，默认中式语境。
- 开局固定为民办、本科，学校可以选择办学性质。
- 学校经营得越好，越有机会申请转为公办。
- 先做“一年一回合”的经营循环，再逐步加入更细的时间颗粒。
- 榜单、招生、审批等均为游戏化模拟，不声称是官方真实数据。
- 使用真实高校名称只用于建立参照感，分数和位次是虚构的。

## 6. 对你五个问题的回答

### 6.1 Git 会自动备份上一个已确认内容吗？

Git 不会在我每次修改时自动提交，需要我主动创建提交。但它能完整保存每一次已提交的版本，所以我会这样做：

- 每个已确认内容完成后，单独提交一次。
- 每次提交写清楚“这次改了什么”。
- 重要的已确认版本打一个标签，例如 `v0.1.0`。
- 提交记录保留在 GitHub，可以随时查看和回退。
- 真正的“自动备份”不会发生，我不能假设某个中间状态已经被保存。

### 6.2 你会自动匹配需要用的 skill 并调用吗？

会。我会根据任务内容匹配已有技能，例如：

- 涉及 Word 文档时用 Word 技能。
- 涉及 Excel 时用 Excel 技能。
- 涉及生成图片时用图片生成技能。

当前这个项目主要是网页代码，不需要额外技能。以后如果做正式版美术、数据表或宣传文档，我会在动手前说明准备调用哪个技能。

### 6.3 我需要插件吗？插件是什么？

对你来说，“插件”不是必须理解的技术细节。可以把它理解为给工具增加能力的扩展。

这个项目目前不需要任何插件。游戏运行只需要浏览器，发布到 GitHub 用的是 Git 和 GitHub 本身。我也不是靠插件工作，而是使用文件、命令、浏览器等工具完成你的需求。

### 6.4 有多智能体统筹吗？

有。当前环境支持把任务拆给多个子智能体并行处理，它们共享同一个工作目录。

但这个项目目前规模不大，我更倾向由我直接按顺序推进，减少多个智能体同时改同一批文件造成的冲突。等需要“并行审计数据、测试页面、核对文案”时，再拆分成多个子任务更合适。

### 6.5 Git 怎么区分哪些文件要上传到 GitHub？

原则是：上传项目运行和协作需要的文件，不上传临时文件、本地配置和秘密。

应该上传：

- 页面和脚本：`index.html`、`styles.css`、`app.js`、`data.js`
- 数据与图标：`manifest.webmanifest`、`icon.svg`
- 工具与说明：`server.js`、`package.json`、`README.md`、`启动游戏.cmd`
- 展示图：`start-screen.png`
- 文档：`docs/`
- GitHub Pages 配置：`.nojekyll`、`.gitignore`

不应该上传：

- `.tools/` 这类临时工具目录
- `.browser-*` 这类浏览器测试目录
- `node_modules/` 依赖目录
- 日志、临时截图、测试生成文件
- GitHub 授权令牌等任何秘密

当前 `.gitignore` 已经排除了临时工具和测试文件；如果以后加入依赖或更多工具，我会继续维护这份忽略清单。

## 7. 我的推荐默认方案

如果你不想逐条选择，我建议按下面执行：

1. **年度节奏**：暂时保持“一年一回合”，先把内容做扎实；等学生生活、师资和就业系统稳定后，再拆成“春季招生 + 秋季运营”两个阶段。
2. **专业目录**：继续使用精选的 192 个专业，把目录做成可扩展结构；只在用户明确提出某类专业时再补充，避免界面冗杂。
3. **难度取向**：采用“规则真实、反馈友好”的混合型。审批和招生保持概率，但失败可重试，不让一次坏运气毁掉整局。
4. **下一阶段优先**：先做“校园生活与人物故事”和“招生生源地图”，让长线经营有具体的人与事件；插画先用代码与矢量图形，等玩法稳定后再做正式美术。
5. **存档方案**：先保持浏览器本地自动存档，并提供 JSON 导入导出；跨设备云端存档需要账号和后端，暂缓。
6. **Git 备份**：每个你确认过的版本打一个标签，例如 `v0.1.0`；每次提交写清楚主题，方便回退。
